# VS-19 — Marketing Lab Shadow Execution

Status: Testing

## Goal
Execute a vetted pinned external marketing challenger in Kairo's Marketing Lab shadow stage against identical synthetic/public-safe benchmark cases, while preserving Kairo Native as the production baseline and all Kairo-owned truth, privacy, spend and publishing controls.

## Requirements
- FR-09 Angle development
- FR-11 Content Studio metadata/provenance
- FR-12 Drafter/Critic/Judge quality evaluation
- FR-16 Performance tracking
- FR-17 Performance Intelligence
- FR-18 Brand Learning
- FR-19 Experiments
- FR-20 Pilot Operations

## Delivered runtime
- `MarketingShadowExecutionService` uses the existing `AgentRuntimePort` with role `strategist`.
- Shadow requests are created through Kairo's validated agent contract with `capabilities: []` and `maxToolCalls: 0`.
- Cost, output-token, timeout and source-text bounds are deterministic Kairo limits.
- Only registered `sandboxed` challengers at `benchmarkStatus=shadow` may execute through this path.
- Challenger permissions must deny network, secrets and publishing; shadow context permission is limited to the scoped benchmark fixture.
- Source repository, exact commit, path, Git blob SHA and byte-exact snapshot content must all agree before runtime invocation.
- External skill text is passed only as `untrustedSkillReference` context. Kairo's instruction, schema, Claims, scope and budget remain authoritative.
- VS-19 accepts only approved synthetic/public-safe Marketing Lab datasets and only Claim-linked carousel/Reel plans.
- Unknown Claim IDs, missing required Claims, prohibited benchmark patterns, format/schema violations and invalid provenance fail closed.
- Benchmark observations are built from separate Kairo-owned truth/quality evaluation plus measured runtime cost/latency; the challenger cannot self-award benchmark scores.
- Paired shadow comparison requires shadow-stage observations and can at most return the existing `advance-to-live` verdict. It cannot qualify or select a Brand skill.

## Defects found and fixed

### Stale source-pin metadata
VS-14's evaluation manifest claimed source hashes that did not match the exact pinned upstream tree for three entries. VS-19 verified the upstream commit tree and corrected:

- `social`: `ab1d083ef4a9dd2a91c1eaedfb5cb745c3055d24`
- `video`: `6c8e9fdeb640594d3bf36690174f1726a721c4e3`
- `content-strategy`: `3a54e3f7b0b23d35d1e4c7f2f608fa947d19061f`

`copy-editing` and `marketing-psychology` already matched the pinned tree.

### Byte-exact Git identity
Self-review found the initial snapshot validator trimmed source text before hashing. Git blob identity is byte-exact, so a legitimate final newline would have been changed and the real upstream snapshot could not verify. Snapshot content is now preserved byte-for-byte, with regression coverage for final-newline identity.

1. Only a registered `sandboxed` challenger with `benchmarkStatus=shadow` is executable by the shadow service. — met.
2. Source provenance exactly matches the pinned GitHub manifest and byte-exact Git blob identity. — met.
3. Shadow invocation has zero tools/capabilities and bounded cost/output/time. — met.
4. External skill text is untrusted reference context and cannot alter Kairo policy fields. — met.
5. Production/private Brand data is excluded; approved synthetic/public-safe fixtures only. — met by bounded input contract/dataset allow-list.
6. Output passes Kairo typed creative and Claim-lineage validation. — met.
7. Truth failure rejects the challenger regardless of marketing scores. — met by paired comparison test.
8. Observations retain Brand/capability/format/case/fingerprint provenance. — met.
9. Shadow success can at most return `advance-to-live`; no qualification or production selection. — met.
10. No network, secret, publishing or infrastructure authority is introduced. — met.
