Design authority:

## Outcome

A Brand can own an optional Presenter profile that Kairo can suggest from Brand context, save as Brand-scoped authoritative state, and use during content creation only when a real configured Avatar provider is healthy. Presenter use remains optional and defaults to `None`.

## User flow

```text
Brand
  → Avatar
  → Create avatar
  → review/accept Kairo suggestions
  → Create & Save
  → optional test clip on same surface

My Idea / For You
  → Presenter selector only when eligible
  → default None
  → Render
  → Preview
  → Approve & Lock
```

## In scope

1. Brand-scoped Presenter profile persistence and optimistic versioning.
2. Presenter fields sufficient for the approved design: name/display label; visual identity/reference asset; voice/language/accent; pace; presentation style; framing; background preference; intro/outro behaviour; caption preference; non-secret provider binding metadata.
3. Kairo-generated Presenter suggestions derived from the existing approved Brand context. Suggestions are proposals, not confirmed Brand facts.
4. Brand → Avatar surface with Create, Save, Edit, Disable and optional Test Clip where provider capability is healthy.
5. Provider-neutral `AvatarProvider` application boundary. No provider SDK or credential in domain/web code.
6. Presenter eligibility projection used by creation surfaces.
7. `Presenter = None` as the default content choice.
8. Presenter rendering feeding the existing Content/Asset Version lineage before human approval.
9. Exact final presenter media shown in Preview and frozen by the existing `Approve & Lock` semantics.
10. Tenant isolation, provenance, private-media handling and fail-closed provider state.

## Out of scope

- AI & Media Providers Settings UI.
- General provider credential management in the product UI.
- Autonomous publishing.
- New primary navigation.
- A separate Presenter content workflow.
- Browser-side direct calls to avatar providers.
- Agent-held provider secrets.
- Production mock providers or fake readiness.
- Voice cloning policy beyond storing an already-approved voice/reference binding.
- Replacing the existing Drafter/Critic/Judge/Renderer pipeline.

## Architecture gate

Issue #188 must be resolved before runtime activation.

Recommended boundary:

```text
Brand / Content application layer
        ↓
PresenterProfile + PresenterEligibility
        ↓
AvatarProvider port
        ↓
configured provider adapter / custom endpoint
        ↓
private generated media
        ↓
validated Content/Asset Version
        ↓
Preview → Approve & Lock → deterministic Publisher
```

PostgreSQL remains authoritative for Presenter state. Object storage remains authoritative for referenced/generated media bytes. Provider state is advisory and replaceable.

## Proposed API contract

Illustrative only until #188 is approved:

- `GET /api/v1/brands/:brandId/presenter`
- `POST /api/v1/brands/:brandId/presenter/suggestions`
- `PUT /api/v1/brands/:brandId/presenter`
- `POST /api/v1/brands/:brandId/presenter/test-clip`
- `POST /api/v1/brands/:brandId/presenter/disable`

Creation/read projections expose presenter eligibility; they do not expose credentials or raw provider diagnostics. All writes require authenticated Workspace/Brand access and optimistic concurrency where replacing persisted profile state.

## State model

Presenter profile state: `draft`, `ready`, `provider-unavailable`, `disabled`.

`ready` requires both a saved valid profile and a healthy configured provider binding. A saved profile with no healthy binding is not eligible for creation and must not be shown as ready.

Test clip state is separate and may be `not-requested`, `queued`, `processing`, `ready`, or `failed`.

## Security and privacy

- Every Presenter record carries `workspace_id` and `brand_id`.
- Visual/audio references are private objects by default.
- Provider credentials remain server-side secret/configuration material.
- External provider responses are untrusted and schema-validated before persistence.
- Generated media is accepted only after Kairo validates Brand scope, content type, size/hash and provider task lineage.
- No cross-Brand Presenter selection or media retrieval.
- No provider can publish directly.
- Signed public URLs, if required for a provider, are temporary and generated only at the adapter boundary.

- [ ] Presenter profile cannot be read or changed cross-Brand.
- [ ] No-provider state renders truthfully and does not expose a production-ready Presenter selector.

- [ ] Test Clip is optional and same-surface; provider failure is explicit and non-destructive.

- [ ] Presenter rendering produces private media with immutable Content/Asset lineage.
- [ ] Preview shows the exact final presenter media intended for publication.

- [ ] Provider credentials, endpoints and raw scopes are absent from normal Presenter UX.
