## Outcome

A Brand can keep one optional presenter profile that expresses how the Brand should appear and sound when a presenter is useful. Profile state is authoritative Kairo data; runtime eligibility is a separate fail-closed projection that also requires a healthy configured `AvatarProvider`. Creation can choose an eligible presenter or `None`; `None` remains the default. This slice never pretends avatar rendering exists when no provider is configured.

## In scope

1. Add Brand-scoped presenter persistence with optimistic versioning and strict Workspace + Brand ownership.
2. Add authenticated API read/write contracts for the Brand presenter profile.
3. Add an optional `Avatar` Brand sub-surface, not a primary navigation destination.
4. Support the approved presentation modes:
   - Basic presenter
   - Talking avatar
   - Hybrid explainer
5. Seed an editable suggested setup from existing Brand context without silently converting suggestions into confirmed Brand truth.
6. Add a replaceable server-side `AvatarProvider` capability port with a fail-closed unavailable default.
7. Derive Presenter eligibility from both saved profile state and provider capability.
8. Let creation choose an eligible Brand presenter or `None`; default is `None`.
9. Persist the optional presenter reference on the durable simple-creation request and return it in the creation view.
10. Fail closed when a presenter ID does not belong to the authenticated Workspace + Brand or when provider rendering capability is unavailable.
11. Show test/render capability truthfully. With no configured Avatar provider adapter, test clip/rendering is unavailable rather than simulated.
12. Preserve all existing exact-version approval, human review, publishing, tenant-isolation and credential boundaries.

## Explicit non-goals

- No avatar video generation or test-clip provider execution.
- No MuseTalk or other provider hard-coding.
- No provider API keys, tokens, endpoint configuration or secret persistence.
- No worker/media-orchestrator changes.
- No automatic presenter selection.
- No face/voice cloning, biometric enrollment or raw identity-media upload.
- No change to approval locks, publisher behavior, Calendar, Insights or channel OAuth.
- No production deployment without later exact-SHA certification, release and production-enable approval.

## Architecture boundary

`DEC-012` establishes:

```text
Brand-scoped PresenterProfile (PostgreSQL authority)
  + AvatarProvider capability port (replaceable, server-side)
  + private media when generation is later enabled
  -> PresenterEligibility projection
  -> optional creation selection
  -> exact Content / Asset Version lineage
  -> Preview -> Approve & Lock -> deterministic Publisher
```

Provider capability is advisory runtime state, not Brand truth. Provider credentials/endpoints remain server-side and are not represented in Presenter contracts or normal UI.

## Data contract

`brand_presenters` stores one optional profile per `(workspace_id, brand_id)` with:

- stable `id`
- `display_name`
- profile `status`: `draft | ready | disabled`
- `mode`: `basic | talking-avatar | hybrid-explainer`
- descriptive presentation preferences: visual style, voice style, language/locale, accent, pace, framing, background, intro/outro style and caption preference
- integer `version`
- timestamps

No provider secret or raw biometric artifact is stored.

`simple_creation_requests.presenter_id` is nullable and references `brand_presenters(id)`. A profile with `status=ready` is only creation-eligible when the server-side Avatar provider reports configured + avatar-rendering capability for the same Brand scope.

## API

- `GET /api/v1/brands/:brandId/presenter`
  - authenticated + Brand-authorized
  - returns `{ presenter, capabilities, eligibility }`
  - capabilities include provider configuration/render/test-clip readiness without credentials or raw diagnostics
  - eligibility is separate from persisted profile state
- `PUT /api/v1/brands/:brandId/presenter`
  - authenticated + Brand-authorized
  - create or exact-version update
  - returns saved presenter + capability/eligibility projection
- existing `POST /api/v1/brands/:brandId/simple-creations`
  - accepts optional `presenterId`
  - validates same Brand + Workspace, enabled profile state, and healthy Avatar rendering capability before persistence

## UX contract

### Brand → Avatar

No presenter:
- compact explanation
- suggested profile derived from current Brand context
- editable presenter mode and presentation preferences
- primary `Create & Save`

Existing presenter:
- presenter summary first
- `Manage` / edit locally
- profile state can be disabled without deleting history

Profile state and runtime eligibility are visually distinct:
- `Enabled` means the profile may be used when provider capability is healthy
- `Ready to select` appears only when eligibility is truly `eligible`
- provider-unavailable state is explicit and non-destructive
- no fake Test Clip button

### Creation

- Presenter selector appears only when `eligibility.status === "eligible"`.
- First option is always `None` and remains the default.
- The selector is contextual, secondary to goal/input/format.
- Server-side validation repeats the eligibility check so a forged presenter ID cannot bypass the UI.
- Choosing a presenter persists the selected ID on the durable creation request.
