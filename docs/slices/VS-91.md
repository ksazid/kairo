# VS-91 — Frozen UI Conformance: Foundation and Shared Shell

## Objective

Normalize Kairo's shared visual system and authenticated product shell to the approved/frozen UI baseline before individual frozen pages are implemented.

This is a design-conformance slice, not a redesign. `product/DESIGN.md`, the latest explicit Product Owner approvals, and `product/UI-IMPLEMENTATION-CONTRACT-2026-08-25.md` are authoritative.

## Approved requirements

- FR-01 Account and Workspace
- FR-02 Brand creation/context
- FR-03 Brand Brain context
- FR-05 Channels navigation context
- FR-11 Content Studio navigation context
- FR-14 Calendar and scheduling navigation context
- FR-16 Performance tracking / Results navigation context
- FR-20 Pilot operations and controls, only where already represented by secondary account/settings surfaces

## Scope

1. Normalize shared design tokens to the approved palette, typography, spacing, radii, semantic states and restrained elevation.
2. Normalize shared controls and reusable UI-state primitives without inventing new product controls.
3. Make the authenticated desktop sidebar conform to the approved order and exactly five primary product destinations: Home, Content, Calendar, Results, Brand.
4. Make the mobile header and bottom navigation conform to the frozen shell contract.
5. Preserve Brand switching, notifications, light/dark appearance, profile/settings access, authentication and existing route/data behavior.
6. Isolate shell chrome from legacy page CSS so page-specific styles cannot redefine the shell.
7. Remove shell-level design drift that is not part of the approved frozen shell.
8. Add deterministic shell-contract tests suitable for later visual-regression capture.

## Explicit exclusions

- No Home, Content, Calendar, Results, Brand, Avatar or Settings page redesign in this slice beyond what is strictly necessary for the shared shell.
- No backend/provider/publishing/billing/analytics functionality implementation.
- No Integrations page implementation.
- No release, production enablement or production deployment.
- No modification of protected infrastructure or release workflow paths.

## UI-first functionality-gap rule

Unavailable functionality must not remove or redesign approved UI. If a shell-related behavior is missing, render the truthful approved state and record it in the Functionality Gap Register in `product/UI-IMPLEMENTATION-CONTRACT-2026-08-25.md`.

## Acceptance criteria

- Desktop authenticated shell uses one 240–248px persistent left rail and exactly five primary product destinations in the approved order.
- Mobile bottom navigation uses exactly five equal-width destinations in the approved order and no `More` item.
- Mobile header contains Brand context/page label plus exactly Notifications, light/dark toggle and Profile/Settings utilities.
- Persistent shell contains no unapproved floating/product-guide control.
- Shell does not show technical workflow destinations.
- Inter/tokenized typography, approved neutral palette and `#4F46E5` primary remain authoritative in light mode.
- Focus, keyboard semantics, touch targets and reduced-motion behavior remain accessible.
- Existing auth, Brand switching, notification retrieval, theme persistence and route construction continue to work.
- Deterministic tests verify shell navigation/order and prohibited shell items.
- `npm run governance:validate` and `npm run preflight` must pass before readiness is claimed.

## Evidence required

- Source diff for tokens/shell/primitives.
- Deterministic tests.
- Desktop and mobile screenshots against the frozen shell reference before certification.
- Functionality-gap reconciliation.
