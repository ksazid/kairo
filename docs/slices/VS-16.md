# VS-16 — Auth0 Identity Provider Migration

Status: Approved and active — runtime implementation authorized outside production

## Goal
Replace the Neon-specific web authentication implementation with Auth0 while preserving Kairo's provider-neutral OIDC boundary and Kairo-owned Workspace/Brand authorization.

## Requirement IDs
- FR-01

## Decision authority
- DEC-001 — managed standards-based OIDC/OAuth behind a Kairo-owned provider-neutral identity/session adapter.

## User-visible outcome
A user can sign in or sign up through Auth0 Universal Login, including Google when the Auth0 Google connection is enabled, then access the same Kairo Workspace/Brand flows with no change to tenant authorization semantics.

## In scope
- Auth0-compatible Authorization Code + PKCE flow through the existing `openid-client` dependency.
- `/auth/login`, `/auth/callback` and `/auth/logout` web routes.
- Email/password signup/sign-in delegated to Auth0 Universal Login rather than collected by Kairo.
- Direct Google entry through Auth0's `google-oauth2` connection when enabled.
- Auth0 API audience `urn:kairo:api` access tokens forwarded to the existing Fastify API.
- Preserve the existing provider-neutral API JWT verifier and Workspace/Brand membership enforcement.
- Remove runtime dependence on Neon Auth routes/client code; dependency-package cleanup may remain deferred if changing the dependency lock is not required for runtime correctness.
- Deterministic auth-flow tests, failure states and documentation for required environment variables.

## Non-goals
- Migrating or importing Neon Auth users.
- Changing Workspace/Brand membership or authorization truth.
- Changing database schemas.
- Enterprise SSO, Organizations, MFA policy, passwordless, RBAC or billing.
- Production deployment, release or production enablement.
- Kairo-owned Google OAuth credentials; Auth0 developer Google credentials may be used only for bounded testing until production credentials are separately configured.

## Acceptance criteria
1. Kairo no longer collects or handles user passwords.
2. Login uses Authorization Code + PKCE with state validation.
3. Callback accepts only the expected transaction and sets the API access token in an HttpOnly, Secure-in-HTTPS, SameSite=Lax cookie.
4. The requested Auth0 audience is `urn:kairo:api` and the API continues to validate issuer/audience/JWKS through its existing OIDC verifier.
5. Google login enters through Auth0 rather than a separate Kairo identity path.
6. Local logout removes Kairo's access-token cookie and uses the provider's discovered end-session endpoint when available.
7. Workspace/Brand authorization behavior is unchanged and remains server-side in Kairo.
8. No Auth0 Client Secret or other secret is committed to Git.
9. Production deployment remains blocked pending exact-SHA certification, release approval, environment configuration and production-enable approval.
