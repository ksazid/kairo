# VS-72 — Auth Callback Session Loop Repair

Status: Approved and active — bounded corrective runtime implementation

## Goal
Restore FR-01 sign-in after the production VS-71 deployment exposed a callback-to-product redirect loop in which Auth0/Google completed the callback but Kairo did not retain a usable browser access-token session.

## Requirement
- FR-01 — Account and Workspace.

## Decision authority
- DEC-001 — managed standards-based OIDC/OAuth behind a Kairo-owned provider-neutral identity/session adapter.
- VS-16 — Auth0 Identity Provider Migration.
- VS-25 — Auth0 Production-Readiness Correction.

## Confirmed production evidence
- Vercel production was running VS-71 merge `ade8ce09733531e95ca44d1b7eec5b24c233fd67` when the issue was reproduced.
- The browser repeatedly traversed `/auth/login` → Auth0/Google → `/auth/callback` → `/` and then restarted authentication.
- Vercel recorded repeated HTTP 307 responses for `/auth/login`, `/auth/callback` and `/` during the reproduction window.
- The callback implementation writes the Auth0 API access token directly to one HttpOnly browser cookie before redirecting to the product shell.
- The Kairo API received no session request during the reproduced loop, which is consistent with the web tier not seeing a usable access-token cookie on the next request.
- The exact access-token byte length was not logged and must not be logged; the repair therefore removes single-cookie size fragility rather than claiming an unobserved token length as fact.

## In scope
- Keep Authorization Code + PKCE, signed transaction state, Auth0 audience and existing API JWT verification unchanged.
- Store access tokens in one cookie when small and split larger tokens into bounded HttpOnly cookie chunks that remain below common per-cookie browser limits.
- Reassemble chunked tokens only inside Kairo server-side web code.
- Add a post-callback `/auth/complete` check that verifies the browser retained the session and the Kairo API accepts the token before entering the product shell.
- Fail to the existing Kairo sign-in recovery page instead of returning to `/auth/login` when cookie retention, API validation or auth transport fails.
- Clear all legacy/chunked access-token cookie variants on authentication failure and logout.
- Add deterministic regression tests for chunking/reassembly and completion outcomes.

## Out of scope
- Changing Auth0 tenant, Google connection, client ID, API audience, issuer or JWKS policy.
- Refresh tokens or a new persistent server-side session store.
- Workspace/Brand authorisation changes.
- API authentication-policy changes or database migrations.
- MFA, Organizations, enterprise SSO or RBAC.
- Release, production enablement or deployment without later exact-SHA approval.

## Acceptance criteria
1. Existing small access tokens remain compatible with the current single-cookie session format.
2. A token larger than one safe cookie payload is split into bounded HttpOnly/Secure-in-HTTPS/SameSite=Lax cookie parts and reassembled exactly on the server.
3. Incomplete or malformed chunk state fails closed and is never sent to the API as a bearer token.
4. The callback routes through `/auth/complete` before entering the requested product path.
5. `/auth/complete` reaches the requested same-origin path only after `/api/v1/session` accepts the bearer token.
6. Missing/rejected session cookies or API failures land on the sign-in recovery state and cannot create the observed infinite redirect loop.
7. Logout clears both legacy and chunked access-token cookies.
8. No token, client secret or provider response body is added to logs, URLs or user-visible errors.
9. Existing PKCE, signed transaction, same-origin return path and Auth0 discovery tests remain green.
10. A real iOS Safari Google-login production smoke is required after exact-SHA certification and deployment.
