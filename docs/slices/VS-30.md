# VS-30 — Unified Multi-channel Publishing Gateway

## Status

Active implementation slice under owner standing pre-approval dated 2026-08-17.

## Goal

Turn Kairo's existing deterministic per-channel publishing foundation into one destination-neutral publishing gateway that can distribute one approved Campaign/Content Version to one or more supported channel accounts while preserving per-destination approval, capability checks, idempotency, retries, reconciliation, auditability and explicit failure state.

The gateway must extend the existing `PublishCommand` + `PublishingAdapter` architecture. It must not create a second publishing subsystem.

## Product authority

- FR-05 — Channels
- FR-10 — Campaign
- FR-13 — Approval workflow
- FR-14 — Calendar and scheduling
- FR-15 — Publishing
- FR-20 — Pilot Operations and Controls

The approved PRD already requires multi-channel support, Campaign-level multiple channel executions, human approval, simple cross-channel scheduling and deterministic publishing.

## Dependencies

- Existing `packages/domain/src/publishing.ts`
- Existing `PublishingJobRunner` / `DeterministicPublishingWorker`
- Existing Instagram and LinkedIn publishing adapters
- VS-15 Instagram image/carousel/Reel publishing contracts
- VS-29 Instagram production publishing executor and E2E contract coverage

## In scope

1. Introduce one application-owned multi-destination publishing entrypoint.
2. Preserve one authoritative `PublishCommand` per destination/account so retries, unknown outcomes and failures remain isolated.
3. Allow a single reviewed Campaign/Content Version to receive explicit approval for multiple selected destinations.
4. Validate each destination independently against account state, channel capability, approved version and content/media shape.
5. Reuse the deterministic adapter execution path; do not create provider-specific orchestration branching.
6. Return normalized per-destination results: scheduled, manual-required, unsupported, reconnect-required or rejected by deterministic policy.
7. Preserve idempotency per destination/version/account and prevent duplicate fan-out on request retries.
8. Keep provider credentials behind the existing credential resolver/vault boundary; no token enters domain state, API payloads or logs.
9. Keep `manual` as a safe degradation destination for unsupported/unconnected channels.
10. Add deterministic unit/integration tests covering mixed-destination fan-out and partial failure.
11. Keep the API/provider boundary extensible so later channel-specific content adapters can plug in without changing Campaign lineage.
12. Add the narrow schema evolution needed to store more than one destination approval for the same content version.

## Explicit non-goals

- No new social network in this slice.
- No autonomous approval or publication.
- No redesign of Calendar or Content Studio.
- No analytics ingestion changes.
- No media transformation pipeline.
- No Creative Blueprint/video-generation work.
- No copying provider credentials between environments.
- No production deployment/publication without its own governed exact-SHA gates.

## Core invariant

`One user distribution action may fan out, but every external destination remains an independently approved, auditable deterministic command.`

## Target flow

```text
Passed Content Version
          |
          v
User selects destinations
          |
          +--> Approval: Instagram account A
          +--> Approval: LinkedIn account B
          |
          v
  PublishingGateway
          |
          +--> PublishCommand A -> Instagram adapter
          +--> PublishCommand B -> LinkedIn adapter
          `--> Manual/unsupported -> explicit non-automatic result
```

## Acceptance criteria

1. Multi-destination requests never bypass review, approval or current-version checks.
2. Each automatic destination has an explicit destination-bound `ContentApproval`.
3. One failing destination cannot make another successful destination appear failed or vice versa.
4. Replaying the same distribution request does not create duplicate effective publication commands.
5. Channel/account capability mismatch fails before provider execution.
6. Provider secrets remain absent from command payloads, persisted content state and logs.
7. Existing Instagram/LinkedIn adapter tests remain green.
8. Existing single-destination APIs remain backward compatible.
9. Deterministic tests cover mixed Instagram + LinkedIn + manual/unsupported destinations.
10. Governance, migrations registry, preflight, CI, Security and Product Intake pass before certification.
