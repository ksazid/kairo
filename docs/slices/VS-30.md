# VS-30 — Unified Multi-channel Publishing Gateway

## Status

Active implementation slice under owner standing pre-approval dated 2026-08-17.

## Goal

Turn Kairo's existing deterministic per-channel publishing foundation into one destination-neutral publishing gateway that can distribute one Campaign action to one or more supported channel accounts while preserving the appropriate channel-specific Content Asset/Version, per-destination approval, capability checks, idempotency, retries, reconciliation, auditability and explicit failure state.

The gateway extends the existing `PublishCommand` + `PublishingAdapter` architecture. It does not create a second publishing subsystem.

## Product authority

- FR-05 — Channels
- FR-10 — Campaign
- FR-13 — Approval workflow
- FR-14 — Calendar and scheduling
- FR-15 — Publishing
- FR-20 — Pilot Operations and Controls

The approved PRD already requires multi-channel support, Campaign-level multiple channel executions, human approval, simple cross-channel scheduling and deterministic publishing.

## Dependencies

- Existing `packages/domain/src/publishing.ts`
- Existing `PublishingJobRunner` / `DeterministicPublishingWorker`
- Existing Instagram and LinkedIn publishing adapters
- VS-15 Instagram image/carousel/Reel publishing contracts
- VS-29 Instagram production publishing executor and E2E contract coverage

## In scope

1. Introduce one application-owned multi-destination publishing entrypoint at Campaign level.
2. Preserve one authoritative `PublishCommand` per destination/account so retries, unknown outcomes and failures remain isolated.
3. Allow a reviewed Content Version to receive explicit approval for multiple selected destinations when appropriate.
4. Allow one Campaign distribution action to reference separate channel-specific assets/versions for Instagram, LinkedIn and later destinations.
5. Validate each destination independently against account state, channel capability, approved version and content/media shape.
6. Reuse the deterministic adapter execution path; do not create provider-specific orchestration branching.
7. Return normalized per-destination results: scheduled, manual-required, unsupported, reconnect-required or rejected by deterministic policy.
8. Preserve idempotency per destination/version/account and prevent duplicate fan-out on request retries.
9. Keep provider credentials behind the existing credential resolver/vault boundary; no token enters domain state, API payloads or logs.
10. Keep `manual` as a safe degradation destination for unsupported/unconnected channels.
11. Add deterministic unit, API and PostgreSQL integration tests covering mixed-destination fan-out and partial failure.
12. Keep the API/provider boundary extensible so later channel-specific content adapters can plug in without changing Campaign lineage.
13. Add the narrow schema evolution needed to store more than one destination approval for the same content version.
14. Keep legacy JSON-only approval inserts compatible while synchronising the new destination lookup columns.

## Explicit non-goals

- No new social network in this slice.
- No autonomous approval or publication.
- No redesign of Calendar or Content Studio.
- No analytics ingestion changes.
- No media transformation pipeline.
- No Creative Blueprint/video-generation work.
- No copying provider credentials between environments.
- No production deployment/publication without its own governed exact-SHA gates.

## Core invariant

`One user distribution action may fan out, but every external destination remains an independently approved, auditable deterministic command.`

## Target flow

```text
Campaign
  |
  +--> Reviewed Instagram Asset Version -- explicit IG account approval -- PublishCommand A
  |
  +--> Reviewed LinkedIn Asset Version  -- explicit LI account approval -- PublishCommand B
  |
  `--> Manual/unsupported destination   -- explicit safe result, no provider execution
```

## Acceptance criteria

1. Multi-destination requests never bypass review, approval or current-version checks.
2. Each automatic destination has an explicit destination-bound `ContentApproval`.
3. One failing destination cannot make another successful destination appear failed or vice versa.
4. Replaying the same distribution request does not create duplicate effective publication commands.
5. Channel/account capability mismatch fails before provider execution.
6. Provider secrets remain absent from command payloads, persisted content state and logs.
7. Existing Instagram/LinkedIn adapter tests remain green.
8. Existing single-destination APIs remain backward compatible.
9. Deterministic tests cover mixed Instagram + LinkedIn destinations and reconnect-required partial failure.
10. PostgreSQL tests prove multiple destination approvals, duplicate approval idempotency and legacy insert compatibility.
11. Review status never presents an approval for an older content version as current authority.
12. Governance, migrations, preflight, CI, Security and Product Intake pass before certification.
