# VS-70 — Publish Now

## Goal

Make immediate human-authorized publishing the primary action for a publish-ready approved Content Version without bypassing Kairo's existing deterministic publishing command, worker, destination, idempotency, retry, reconciliation or audit controls.

## Requirements

- FR-13 — Approval workflow
- FR-14 — Calendar and scheduling
- FR-15 — Publishing

## Scope

1. Preserve destination-specific human approval as a hard prerequisite.
2. Allow the existing publishing service to treat an omitted `scheduledFor` value as an explicit publish-now request.
3. Capture one server timestamp and use it for both `createdAt` and immediate `scheduledFor`, avoiding client/server clock races.
4. Preserve duplicate prevention: repeating the same immediate request for the same approval returns the existing immediate command; a conflicting future schedule remains a conflict.
5. Dispatch immediate commands through the existing durable publishing worker and channel adapters. The web request must not call social-provider APIs directly.
6. Make **Publish now** the primary Content Studio action where the current web path has a complete publishable payload. In this slice that is LinkedIn text.
7. Keep **Schedule for later** available as a secondary, progressively disclosed action.
8. Keep success semantics truthful: the UI says the item is queued until the existing worker records an external publication result.

## UX read

Content Studio is an authenticated, content-first workflow. The user job after exact-version approval is to publish with minimal friction while retaining an optional future schedule. Primary emphasis belongs to Publish now; scheduling remains available without competing visually.

Desktop, tablet and mobile retain the same action hierarchy. All actions remain keyboard-operable and labelled; no hover-only interaction is introduced.

## Acceptance criteria

- An approved LinkedIn text version can be queued with one **Publish now** action.
- The resulting command has `scheduledFor === createdAt` using a server-generated timestamp and begins in the existing `scheduled` state.
- The worker, not the web request, performs provider dispatch.
- A repeated identical Publish now request does not create a second command.
- A pre-existing different future schedule is not silently accelerated or overwritten.
- Existing scheduled publishing remains functional and user-accessible.
- Existing retry, unknown-state reconciliation, idempotency keys, external post ID persistence and destination scoping are unchanged.
- The UI never claims `published` before provider-confirmed settlement.

## Explicit exclusions

- No autonomous or policy-based publishing.
- No approval bypass or change to FR-13 human authority.
- No direct Meta, LinkedIn or other provider call from the web application.
- No provider credentials in the browser or agent runtime.
- No publishing worker, retry, reconciliation, idempotency or channel-adapter redesign.
- No removal of Calendar or scheduled publishing.
- No account-group behavior change.
- No Instagram media transformation, public-media URL generation or Google Drive-to-provider media handoff. Instagram rich-media immediate publishing remains on its existing media-aware path until a separately governed slice supplies a complete publish-ready media payload.
- No provider/model, Hermes, Marketing Lab, VS-23 or VS-24 changes.
- No deployment, release, production enablement or merge in this implementation gate.

## Risk

High. This changes a user-facing path that can result in external publication, but it does not expand publication authority: exact-version human approval and the deterministic publishing boundary remain mandatory.
