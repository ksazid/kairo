# VS-62 — Instagram Retry-After correctness

## Requirement

FR-15 Publishing and Scheduling.

## Problem

The Instagram publishing adapter marks HTTP 429 and 5xx responses retryable, but when Meta omits `Retry-After` it provides no pacing hint. Some transient Meta error envelopes can also arrive on non-429 HTTP responses and should be classified consistently without retrying inside the adapter.

Tracked by GitHub issue #89.

## Scope

- Preserve a valid provider `Retry-After` hint when present.
- For Instagram responses without `Retry-After`, derive a small bounded fallback hint for:
  - HTTP 429 / Meta rate-limit codes 4, 17, 613;
  - HTTP 5xx / Meta `is_transient: true` errors.
- Keep non-transient/auth/permission errors non-retryable unless their HTTP status is independently transient.
- Return the hint to the existing publishing planner; do not retry inside the adapter.
- Add focused regression coverage for header precedence, 429/5xx fallback, Meta transient envelopes, non-retryable errors, and single provider-call behavior.

## Non-goals

- No OAuth, Meta app, permission, credential, account, or provider configuration changes.
- No publishing scheduler/executor redesign.
- No new provider scope.
- No deployment, release, production enablement, or live provider call.
- No UI change.

## Acceptance criteria

1. A retryable Instagram 429 without `Retry-After` returns a bounded retry hint.
2. A retryable Instagram 5xx without `Retry-After` returns a bounded retry hint.
3. Meta rate-limit/transient envelopes receive the appropriate retry classification and bounded hint even when HTTP status alone is not retryable.
4. A valid `Retry-After` response header takes precedence over fallback logic.
5. Non-transient/auth failures do not receive a fallback retry hint.
6. The adapter makes no internal retry attempt; the existing outer planner remains responsible for retry execution.
7. Product Intake, Security baseline, and CI pass on one frozen exact candidate SHA.
