# VS-01 — Account, Workspace and Brand

Status: Approved and active — runtime implementation authorized

## Goal
Establish secure account, Workspace and Brand boundaries plus the authenticated web shell required by every later slice.

## Requirement IDs
- FR-01
- FR-02

## User-visible outcome
A user can authenticate, create or join a Workspace, create the first Brand, switch only among authorised Brand contexts and reach the Kairo shell.

## In scope
- Account/session contracts using the approved managed standards-based OIDC/OAuth approach behind a Kairo-owned provider-neutral adapter (DEC-001).
- Workspace ownership/membership foundation and server-side authorisation.
- Lightweight Brand creation with name plus optional public source/profile inputs.
- PostgreSQL schema/migrations for Account, Workspace, membership and Brand.
- Kairo web shell and approved design-token foundation.
- Fastify transport boundary for the modular TypeScript API (DEC-002).
- Tenant-isolation, audit, accessibility and error-state coverage.

## Non-goals
- Brand Brain enrichment or document ingestion.
- Hunter, generation, publishing, metrics or billing.
- Enterprise access hierarchy.
- Production deployment or production-enable behavior.

## Dependencies and gates
- DEC-001 approved: managed standards-based OIDC/OAuth behind a provider-neutral adapter.
- DEC-002 approved: Fastify transport boundary.
- Scope approval recorded 2026-08-12.
- Runtime implementation approval recorded 2026-08-12.
- Certification, release and production-enable approvals remain separate future gates.

## Acceptance criteria
1. Unauthorised users cannot access Workspace/Brand data.
2. A user can create the initial Workspace and Brand using minimal inputs.
3. Brand identifiers never act as authorisation by possession alone.
4. Web shell follows the approved minimalist Kairo Design Baseline.
5. Migrations and tenant-isolation tests are deterministic.
6. Identity-provider code remains adapter-bound and does not become Workspace/Brand authorization truth.
7. Fastify remains at the transport edge; domain/application modules do not depend on it.
