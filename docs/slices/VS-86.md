# VS-86 — Shell Normalization and Recovery Navigation

## Status
Scope and implementation direction approved by the Product Owner on 2026-08-24 after the final Kairo UI review. Runtime implementation is authorised. Certification, merge, release, production enablement and deployment remain separate exact-SHA gates.

Production-dependent verification is intentionally deferred until deployment capacity is available; this slice may be implemented and verified locally/through CI without production rollout.

## Outcome
Normalize Kairo's shared navigation and recovery paths so every current surface presents the approved product language and routes users to useful recovery locations without exposing legacy information architecture.

The user-facing primary navigation is:

```text
Home
Content
Calendar
Insights
Brand
```

The existing internal `Results` / `/performance` identifiers may remain temporarily for compatibility. User-facing copy should render `Insights`.

## In scope

### Shared primary navigation
1. Keep exactly five primary destinations on desktop and mobile.
2. Render the existing internal Results destination as user-facing `Insights` without requiring a risky route/domain rename in this slice.
3. Remove `More` from remaining legacy mobile navigation.
4. Normalize remaining legacy navigation helpers to the same five user-facing destinations so older Calendar/Formats surfaces do not expose Today/Discover/Ideas/Campaigns/Performance/Brand Brain as primary navigation.
5. Preserve the approved Kairo wordmark, Brand context and existing route destinations.

### Notifications and recovery routing
6. A publishing-failure notification should deep-link to the affected Content/Campaign context when lineage is available, with Content as the safe fallback.
7. An Instagram reconnect notification should deep-link to the existing Instagram recovery/connect route rather than Performance/Insights.
8. Other connection issues must route to a Brand recovery surface rather than analytics.
9. No notification may claim provider success before the underlying state is settled.

### Settings entry
10. Replace the disabled `Settings · Later` profile entry with a real Settings route.
11. The first Settings surface remains intentionally small: Appearance and account-level utility only.
12. AI & Media Provider management remains a later dedicated implementation slice; VS-86 must not fake provider configuration controls.

### Compatibility boundary
13. Do not rename persisted domain types, database values, API contracts or `/performance` routes solely to achieve the Insights label.
14. Do not redesign Calendar, Content, Brand or Insights in this slice.
15. Do not alter authentication, publishing authority, provider scopes, Brand isolation or approval semantics.
