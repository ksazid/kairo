# VS-27 — Hermes Runtime Integration

Status: Approved for bounded implementation

## Goal
Activate the already-approved Hermes reasoning-runtime boundary so Kairo can execute real model-backed agent work without exposing provider credentials to Kairo agents or domain code.

## Requirement IDs
- FR-12 — Drafter, Critic and Judge
- FR-20 — Pilot Operations and Controls

This slice is a cross-cutting runtime enabler for already-approved AI behaviour. It does not add a new user-facing product requirement.

## Approved architecture
The approved TRD already defines `AgentRuntimePort -> Hermes preferred / DirectModelRuntime fallback` and permits `services/hermes-runtime/` when Hermes is adopted. This slice activates that existing boundary; it does not replace Kairo's modular-monolith domain architecture.

## In scope
- Pin an evaluated Hermes Agent upstream release and exact commit.
- Add a Kairo-owned Hermes runtime service exposing only the versioned `/kairo/v1/invoke` contract expected by `HermesBridgeRuntime`.
- Enforce bearer service authentication and the exact Kairo Hermes policy fingerprint.
- Enforce a zero-tool reasoning profile; startup/invocation must fail closed if Hermes exposes tools.
- Disable Hermes project-context injection, persistent memory, skills/plugins and autonomous tool execution for Kairo reasoning calls.
- Keep Groq and OpenRouter credentials inside the Hermes service boundary only.
- Configure Groq as primary inference and OpenRouter as bounded fallback for normal Kairo runtime calls.
- Support a `primary-only` routing mode for controlled benchmarks so baseline/challenger executions cannot silently switch providers.
- Return output plus provider/model/runtime/token/cost/latency provenance to Kairo.
- Wire Kairo API runtime selection as: Hermes when configured; DirectModelRuntime remains independently viable and may be used as fallback when separately configured.
- Add deterministic tests for authentication, zero-tool attestation, policy fingerprint, provider fallback, primary-only mode, JSON parsing, timeouts and secret isolation.
- Add deployment/runbook documentation and environment-variable names only; no secret values.

## Upstream pin
- Repository: `NousResearch/hermes-agent`
- Release/tag: `v2026.7.7.2` / Hermes Agent v0.18.2
- Exact commit: `9de9c25f620ff7f1ce0fd5457d596052d5159596`

Upstream is untrusted infrastructure code. The pin must not move automatically.

## Provider policy
Normal runtime:
1. Groq primary.
2. OpenRouter fallback only after an eligible primary provider failure.

Controlled Marketing Lab qualification:
- `primary-only` mode;
- same provider and model for baseline and challenger;
- fallback disabled for the paired comparison.

Kairo remains authoritative for Brand isolation, approved context, schemas, Claims/Truth policy, budgets, human approval and publishing.

## Non-goals
- No autonomous publishing.
- No Hermes access to social credentials, database credentials, Kairo ToolGateway or unrestricted shell/network tools.
- No general-purpose Hermes chat UI.
- No Hermes memory as Kairo Brand memory.
- No provider/model optimisation based on ungoverned heuristics.
- No production deployment or provider-secret entry in this implementation PR.
- No VS-23 live activation or VS-24 Brand-skill promotion.
- No database migration.

## Security invariants
1. Provider API keys never enter Kairo prompts, Brand Brain, database records, logs or browser code.
2. Kairo sends only the bounded task/context already approved by `AgentRuntimePort`.
3. Hermes must attest the exact policy fingerprint and `enabledTools: []`; Kairo rejects any other response.
4. The Hermes service independently checks that its upstream tool surface is empty before serving traffic.
5. Persistent Hermes memory/context/skills are disabled for Kairo invocations.
6. Service authentication uses a separate Kairo↔Hermes bearer token.
7. Logs contain request identifiers and operational metadata, not Brand-private prompt bodies by default.
8. Benchmark routing is deterministic and cannot fall back to a different provider/model.

## Acceptance criteria
1. A valid authenticated Kairo invocation returns schema-parseable JSON plus Hermes/provider/model/token/cost/latency provenance.
2. Missing/incorrect service token returns 401 without invoking a provider.
3. Wrong policy fingerprint or any requested/enabled tool causes a fail-closed error.
4. Startup refuses to become ready if the pinned Hermes runtime exposes a non-empty tool surface under the Kairo profile.
5. Normal mode uses Groq first and may fall back to OpenRouter only for configured eligible failures.
6. `primary-only` mode never calls OpenRouter.
7. Provider keys are read only from Hermes service environment variables and are absent from Kairo request/response payloads and committed files.
8. Kairo API can instantiate `HermesBridgeRuntime` from environment configuration without requiring any provider API key.
9. DirectModelRuntime remains usable when configured, preserving the approved fallback architecture.
10. Full repository deterministic CI and security gates pass before certification is requested.

This authorizes bounded implementation of this scope but does not authorize merge, release, production deployment, secret entry or production enablement.
