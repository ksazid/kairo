# VS-64 — Marketing Lab One-Shot Benchmark Authorization Fence

## Purpose

Prevent a configured Corey-vs-Native qualification deployment from starting model work until the owner has separately authorized one exact benchmark run against one exact release SHA.

This refresh replaces the stale Hermes-specific assumptions in legacy PR #79. The active qualification route is now Kairo `DirectModelRuntime`; Hermes remains available elsewhere only behind its existing explicit opt-in and is not activated by this slice.

## Scope

VS-64 adds:

- migration `0022_marketing_shadow_evidence_authorizations.sql`;
- at most one outstanding benchmark authorization globally;
- exact `run_id` + `release_sha` binding;
- a durable status lookup that distinguishes `not-authorized`, `authorized`, `started`, `completed` and `failed`;
- atomic authorization consumption plus creation of the durable `started` evidence row;
- exactly-once protection across concurrent/overlapping processes;
- a server polling loop that performs only PostgreSQL control checks while no authorization exists;
- idempotent completion/failure persistence so persistence retries cannot rerun model lanes;
- bounded failure-kind persistence and logging;
- unit and PostgreSQL integration coverage for authorization, concurrency and release binding.

## Runtime invariants preserved

VS-64 does not change the existing paired qualification semantics:

- four approved motorcycle carousel fixtures;
- Native and Corey receive identical transformed inputs;
- eight sequential lanes total;
- 65-second inter-lane pacing;
- 30-second per-lane timeout;
- 2,200 maximum output tokens per lane;
- $0.03 cost ceiling per lane;
- zero tools/capabilities;
- exact pinned Corey source/provenance verification;
- identical DirectModel provider/model/pricing route across compared lanes;
- existing Truth, quality, human-preference and edit-distance policy remains authoritative;
- successful paired execution still does not itself promote Corey or activate VS-23.

## Authorization state machine

```text
not-authorized
      |
      | separate production approval + one authorization row
      v
authorized
      |
      | atomic consume + durable started row
      v
started
   |      |
   |      +--> failed
   v
completed
```

A flag-enabled process with `not-authorized` status performs no model invocation. It polls only the authorization state. Once one process consumes the authorization, every competing process sees `started` (or later terminal state) and stops without invoking the model.

## Production sequence after a future separate approval

1. Certify and merge the exact VS-64 candidate.
2. Obtain a separate deployment approval for an exact Kairo API SHA.
3. Verify the intended production database target and data continuity. Do not change `DATABASE_URL` implicitly.
4. Under a separate production migration approval, apply and verify migration `0022` on that exact database.
5. Verify `marketing_shadow_evidence_authorizations` is empty.
6. Configure one fresh non-secret run ID and the exact release SHA with the benchmark flag enabled, then allow rollout to settle. With no authorization row, zero model work occurs.
7. Obtain a separate explicit one-run benchmark approval.
8. Insert exactly one authorization row with the fresh run ID and exact release SHA.
9. One stable process atomically consumes the row, creates the durable `started` record and executes the existing DirectModel paired qualification.
10. Do not deploy or mutate benchmark configuration while the run is `started`.
11. After `completed` or `failed`, return the benchmark flag to `0` under the approved production procedure.
12. Recover completed evidence for blind human scoring. No winner may be claimed from incomplete evidence.

## Explicit exclusions

This slice does **not**:

- deploy Kairo or Hermes;
- enable Hermes;
- apply migration `0022` to any production database;
- change `DATABASE_URL`;
- insert a benchmark authorization;
- enable or run the benchmark;
- change provider/model/API key/pricing/routing;
- alter benchmark fixtures, prompts, schemas, Truth checks, quality scoring or thresholds;
- use customer, Brand-private, Instagram or social-credential data;
- publish content;
- qualify/promote Corey;
- activate VS-23;
- authorize release or production enablement.

## Acceptance criteria

1. Without an authorization row, a configured attempt returns `not-authorized` and never claims or invokes DirectModel.
2. Only one outstanding authorization can exist globally.
3. An authorization is bound to one exact run ID and release SHA.
4. Exactly one concurrent process can consume the authorization and create the durable `started` row.
5. Competing or restarted processes do not invoke the model after the run is `started`, `completed` or `failed`.
6. Completion/failure persistence is idempotent and does not rerun model lanes.
7. Full CI passes migration verification on clean PostgreSQL 18, governance, tests, typecheck and builds.
8. No deployment, migration application or benchmark execution occurs during implementation/certification.
