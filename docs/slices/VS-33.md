# VS-33 — Channel / Account Groups

## Status

Active implementation slice under owner standing pre-approval dated 2026-08-17.

## Goal

Let Kairo users save reusable, Brand-scoped sets of connected channel accounts and reuse those sets from Content Studio without weakening the deterministic publishing controls established in VS-30.

## Product authority

- FR-05 — Channels
- FR-10 — Campaign Management
- FR-13 — Brand Management and approval workflow
- FR-14 — Calendar / scheduling visibility
- FR-15 — Deterministic publishing

## Dependencies

- VS-30 Unified Multi-channel Publishing Gateway
- VS-32 Visual Content Calendar
- Existing `ChannelAccount`, destination approval and `PublishCommand` contracts

## In scope

1. Create, list, edit and delete named Account Groups inside one Brand scope.
2. Limit each group to 1–20 unique existing channel-account IDs.
3. Never copy or persist provider credentials in group state.
4. Validate every member against the selected Brand before group creation or update.
5. Surface connected and reconnect-required destinations truthfully in group management UI.
6. Allow a reviewed Content Version to be distributed to a selected Account Group by expanding the group into concrete VS-30 destinations.
7. Preserve one destination-specific approval and one deterministic `PublishCommand` per expanded member.
8. Preserve VS-30 capability checks, reconnect handling, duplicate prevention, idempotency and partial-failure semantics.
9. Add PostgreSQL migration 0018 for Brand-scoped group persistence.
10. Add deterministic domain tests for membership, Brand scope and duplicate rejection.
11. Use the approved `product/DESIGN.md` calm, minimal, content-first interaction language and existing Content Studio patterns.

## Explicit non-goals

- No autonomous scheduling or publication.
- No group-level approval authority.
- No single group-level publish command.
- No new provider, OAuth scope or credential flow.
- No cross-Brand or cross-Workspace group membership.
- No provider credential copying.
- No production deployment or migration execution in this slice without a separate exact-SHA release gate.

## Core invariant

`A group is only a reusable destination selector. Expansion must end in the same independently approved, auditable, deterministic destination commands used without groups.`

## Acceptance criteria

1. A user cannot add an account from another Brand to a group.
2. Duplicate account IDs are rejected before persistence.
3. Group state contains account IDs only, never provider secrets.
4. Deleting a group does not delete Channel Accounts or existing Publish Commands.
5. Content Studio can select an existing group only after the current version passed review.
6. Group distribution expands to concrete channel-account destinations and calls the existing VS-30 distribution API.
7. Reconnect-required, disabled, unsupported or otherwise rejected members remain explicit per-destination failures.
8. A successful member is not marked failed because another member fails.
9. Existing single-destination approval/scheduling remains available and backward compatible.
10. PostgreSQL 18 migration, runtime verification, dependency/security checks, Product Intake, UI review and CI must pass before certification.
