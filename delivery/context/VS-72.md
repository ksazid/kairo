- Production web deployment: `dpl_EeJd5LAMrtrvAvSdw8yDSasHVSSV` on exact VS-71 merge `ade8ce09733531e95ca44d1b7eec5b24c233fd67`.
- User reproduced the failure in iOS Safari after Google sign-in.
- Vercel runtime sequence repeated `/` → `/auth/login` → `/auth/callback` → `/`, all HTTP 307 responses, until Safari stopped the redirect chain.
- No corresponding Kairo API session request was observed during the reproduction window.
- `/auth/login` successfully generated the Auth0 authorize request and signed transaction cookie.
- `/auth/callback` exchanged the authorization response sufficiently to redirect back into Kairo; the existing implementation then wrote the Auth0 API access token to a single `kairo_access_token` browser cookie.

## Existing authoritative behavior
- FR-01 requires usable sign-in/sign-out/access recovery.
- DEC-001 keeps identity provider integration behind Kairo's provider-neutral OIDC boundary.
- VS-16 requires Authorization Code + PKCE, signed transaction state, Auth0 audience and HttpOnly API-token bridging.
- VS-25 requires safe/retryable discovery and authentication failure behavior.
- Workspace/Brand authorization remains Kairo-owned and server-side.

## Repair contract
- Preserve legacy single-cookie sessions for small tokens.
- Split larger bearer tokens across bounded server-only cookie parts.
- Add `/auth/complete` as a post-callback checkpoint.
- Require the browser-presented token to pass `/api/v1/session` before entering the product shell.
- Any failure goes to `/sign-in` recovery and clears access-token cookies; it must not automatically restart Auth0 login.
- Logout clears legacy and chunked cookie formats.
