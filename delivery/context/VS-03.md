## Existing foundation

VS-01 provides Account/Workspace/Brand authorization and PostgreSQL authority. VS-02 provides confirmed/inferred/stale Brand Brain context and governed private Knowledge sources. VS-03 must consume those boundaries without creating a parallel tenancy or memory model.

## Domain boundary

### Global Signal

A public Signal is reusable only when visibility policy permits and should retain normalized source/evidence metadata including URL/platform, author or publisher where available, publication/retrieval time, provider provenance, freshness and content hash/duplicate keys.

### Brand Opportunity

A Brand-scoped Opportunity references one or more eligible Signals and retains relevance, novelty, evidence strength, timeliness/evergreen value, concise user-facing rationale, suggested development direction, lifecycle state and the Brand context/version used for scoring.

### Duplicate / novelty check

Novelty compares candidate Opportunities against recent Signals, Ideas, active Campaigns and published content. Similarity alone does not hard-reject a topic when the proposed angle is materially different. No query may cross private Brand scope.

## Agent/runtime boundary

- Kairo owns `AgentRuntimePort`, `ToolGateway`, capability policy, schemas, budgets, provenance and authoritative persistence.
- Hermes is the preferred but replaceable runtime candidate and must pass a focused spike before promotion. `DirectModelRuntime` remains viable fallback.
- Agent Reach is approved by DEC-005 only as a replaceable `DiscoverySourceProvider` / Dynamic Skill behind Kairo ToolGateway.
- Hermes must never receive unrestricted shell access, arbitrary provider credentials, browser cookies/session material or direct database write authority.
- Agent output returns to Kairo for schema/policy/provenance validation before state mutation.

## Model/API-key boundary

Model provider API keys remain server-side secret configuration. Browser clients, Brand Brain, prompts, free-form skill context and persisted domain records never receive raw API keys. Kairo ModelGateway chooses approved provider/model policy by role, privacy, quality, latency and cost; invocation records may retain provider/model/version/token/cost metadata but never secrets.

## UI boundary

Today/Discover must follow the approved Design Baseline:

- short ranked set of worthwhile Opportunities rather than a dense dashboard;
- title, relevance/evidence state, concise rationale/`Why now`, and one dominant Develop action;
- Save and Ignore as secondary actions;
- explicit loading, error, empty/no-strong-opportunity and stale/freshness states;
- Brand context visible without visual clutter;
- responsive collapse to a single primary flow;
- keyboard/screen-reader/focus/touch-target/reduced-motion support.

`design-taste-frontend` is installed but is not the primary skill for this product workflow. Before substantial VS-03 product UI implementation, verify/install the approved product-design skill set referenced by `AGENTS.md` (UI UX Pro Max, Impeccable, Emil Design Engineering and Ponytail where available) rather than claiming they were used when absent. The approved Design Baseline remains authoritative regardless of skill availability.
