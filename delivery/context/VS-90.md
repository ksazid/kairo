## Existing architecture reused

- PostgreSQL is authoritative.
- API uses authenticated Brand authorization through `KairoService`.
- Small vertical capabilities use dedicated store + Postgres adapter + route modules.
- Simple creation already persists a Brand-scoped request before Research/Angle/Campaign work.
- Provider credentials and provider-specific behavior remain behind deterministic infrastructure/adapters.

## VS-90 implementation boundary

Authoritative state:
- one optional Brand presenter profile in PostgreSQL
- optimistic versioning
- nullable durable `presenter_id` on simple creation

Normal UX:
- Brand → Avatar sub-surface
- suggestions derived from existing Brand context, clearly labeled as suggestions
- Basic presenter / Talking avatar / Hybrid explainer
- Presenter appears during creation only when a `ready` presenter exists
- `None` is always first/default

Provider boundary:
- no provider selected or hard-coded
- no secret/config persistence
- no fake test clip
- API exposes only truthful capability availability
- worker/media-orchestrator remains unchanged

## Security / privacy boundary

The presenter profile may contain voice/accent/presentation preferences, so the slice is treated as medium risk with sensitive-data impact. This slice does **not** accept biometric enrollment, raw face/voice samples, or cloning media. Every row is Workspace + Brand scoped and every mutation is authenticated and tenant-authorized.
